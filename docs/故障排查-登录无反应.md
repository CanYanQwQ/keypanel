# 故障排查：后台登录后无反应

本文档记录一个真实线上故障的完整排查过程。现象是：**后台输入正确的邮箱密码，点击登录后没有任何反应，也不报错，停留在登录页。**

最终定位到 **5 个问题叠加**，其中 3 个必须修复、2 个是配置调整。按本文档的顺序排查可快速定位。

---

## 现象描述

| 项目 | 表现 |
| --- | --- |
| 输入框 | 可以正常输入邮箱和密码 |
| 点击「登录」按钮 | 无任何反应 |
| 页面反馈 | 不跳转、不报错、输入框内容保留 |
| `storage/logs/laravel.log` | 无任何错误记录 |
| 数据库账号 | 密码哈希正确、账号未锁定 |

诊断关键点：**Laravel 无日志 = 请求根本没到业务逻辑**，说明问题在前端 JS 或请求链路，而非后端代码。

---

## 问题 1：中文 APP_NAME 导致 Session Cookie 名异常

### 现象

会话无法保持。登录请求实际成功了（服务器返回跳转到 `/admin`），但浏览器跳转回后台时没带上会话 cookie，于是又回到登录页。

### 根因

`config/session.php` 这样生成 cookie 名：

```php
'cookie' => env('SESSION_COOKIE', Str::slug(env('APP_NAME')).'-session'),
```

`Str::slug()` 只保留 ASCII 字母数字。当 `APP_NAME` 是全中文（如「卡密管理系统」）时，slug 结果为空字符串，cookie 名退化成：

```
-session        ← 以短横线开头
```

这种异常名称在部分浏览器 / CDN 组合下会被丢弃或无法正确回传。

### 诊断方法

```bash
# 访问登录页，看 Set-Cookie 的名称
curl -sI https://你的域名/admin/login | grep -i set-cookie

# 异常输出示例（问题状态）
set-cookie: -session=...
# 正常输出示例（修复后）
set-cookie: cardkey_session=...
```

### 修复

**在 `.env` 中显式指定**（推荐，最简单）：

```ini
SESSION_COOKIE=cardkey_session
```

修改后清除缓存：

```bash
php artisan config:clear
php artisan cache:clear
```

**代码层面**已在 `config/session.php` 增加兜底：

```php
'cookie' => env(
    'SESSION_COOKIE',
    (Str::slug((string) env('APP_NAME', 'laravel')) ?: 'cardkey').'-session'
),
```

`install.php` 也会自动写入 `SESSION_COOKIE=cardkey_session`。

## 问题 2：Cloudflare Rocket Loader 改写 script 标签

### 现象

页面能打开，但 Livewire 的 JavaScript 不执行。

### 根因

Cloudflare 的 **Rocket Loader** 会重写页面上所有 `<script>` 标签的 `type` 属性：

```html
<!-- 源站正常输出 -->
<script src=".../livewire.min.js" data-csrf="...">

<!-- 经 Rocket Loader 后 -->
<script src=".../livewire.min.js" type="076a7fcfbafcbb604179cef7-text/javascript" data-csrf="...">
```

被加上随机前缀的 `type` 值浏览器不认识，脚本**不会执行**。Livewire 依赖 `type` 属性判断加载方式，因此完全失效——点击登录没有事件处理器，表现为"点了没反应"。

### 诊断方法

```bash
# 对比源站输出与经 CDN 的输出
curl -s https://你的域名/admin/login | grep -oE 'type="[a-f0-9]+-text/javascript"' | head -3

# 有输出 → Rocket Loader 正在改写
# 无输出 → 正常
```

### 修复

Cloudflare 后台关闭 Rocket Loader：

```
选择域名
  → 速度 / Speed
    → 优化 / Optimization
      → Rocket Loader → 关闭
```

中文界面路径：**速度 → 优化 → 内容优化 → Rocket Loader → 关闭**

> 也可以用 Cloudflare 后台顶部的搜索框直接搜 `Rocket Loader` 跳转。

**注意**：Rocket Loader 与 Laravel Livewire / Filament 是已知的不兼容组合。除它之外，Cloudflare 的其他功能（缓存、DDoS 防护、SSL）都可以正常使用。

## 问题 3：宝塔 Nginx 静态资源规则拦截 Livewire 动态路由

### 现象

Livewire 的 JS 文件返回 **404**，但响应体内容却是完整的 JavaScript 源码（状态码与内容不匹配）。

### 根因

Livewire 4 的 JS 由 Laravel **动态生成**，路由为 `/livewire-{hash}/livewire.min.js`，磁盘上并不存在这个文件。

而宝塔面板默认在站点配置里加了一条静态资源规则：

```nginx
location ~ .*\.(js|css)?$
{
    expires      12h;
    error_log /dev/null;
    access_log /dev/null;
}
```

Nginx 的 `location ~`（正则匹配）优先级**高于** `location /`，所以所有 `.js` 请求都被这条规则拦截，nginx 直接去磁盘找文件 → 不存在 → 404。伪静态里的 `try_files` 根本没机会执行。

### 诊断方法

```bash
# 1. 带参数与不带参数都测
curl -s -o /dev/null -w 'HTTP=%{http_code}\n' 'https://你的域名/livewire-xxxx/livewire.min.js'
curl -s -o /dev/null -w 'HTTP=%{http_code}\n' 'https://你的域名/livewire-xxxx/livewire.min.js?id=xxx'

# 2. 绕过 CDN，直连源站对比
curl -s -o /dev/null -w 'HTTP=%{http_code}\n' \
  'https://127.0.0.1/livewire-xxxx/livewire.min.js' -k -H 'Host: 你的域名'

# 3. 检查磁盘是否存在该目录
ls /www/wwwroot/你的项目/public/livewire-*    # 应报"不存在"，证明是动态路由
```

**判断要点**：如果源站直连返回 200 而经 CDN 返回 404，说明源站已修复、是 CDN 缓存问题（见问题 4）。如果源站也 404，就是本问题。

### 修复

在宝塔站点配置文件（`/www/server/panel/vhost/nginx/你的域名.conf`）中，
**插入到静态资源 `location ~ .*\.(js|css)?$` 之前**：

```nginx
# Livewire 的动态资源路由。
# 必须放在静态资源 location 之前：nginx 中 ^~ 优先级高于正则匹配，
# 否则 /livewire-*/livewire.min.js 会被下面的 js|css 规则拦截当静态文件处理，
# 而该文件并不存在于磁盘（由 Laravel 动态生成），导致 404、Livewire 无法加载。
location ^~ /livewire- {
    try_files $uri $uri/ /index.php?$query_string;
}
```

保存后重载：

```bash
nginx -t && nginx -s reload
```

> **重要**：宝塔面板的「伪静态」设置里写的规则会被面板管理，但
> **`location` 块建议直接写在站点配置文件中**，因为伪静态文件只包含
> `location /` 块，无法调整与其他 location 的优先级顺序。
>
> 另外注意宝塔生成的 `try_files` 规则可能是
> `/index.php?query_string`（缺少 `$`），正确的是 **`$query_string`**。

### 同类问题

除了 `/livewire-`，Laravel 还有其他动态路由也带 `.js`/`.css` 后缀，同样需要加规则：

```nginx
# 如果使用了这些功能，一并加上
location ^~ /livewire-   { try_files $uri $uri/ /index.php?$query_string; }
location ^~ /filament-   { try_files $uri $uri/ /index.php?$query_string; }
```

## 问题 4：Cloudflare 缓存了 404 响应

### 现象

源站已修复（直连返回 200），但经 CDN 访问仍是 404。

### 根因

问题 3 期间产生的 404 响应被 Cloudflare 缓存了。响应头显示：

```
cache-control: public, max-age=31536000    ← 缓存 1 年
cf-cache-status: HIT
age: 1335
```

### 诊断方法

```bash
# 带一个随机参数，绕过缓存
curl -s -o /dev/null -w 'HTTP=%{http_code}\n' \
  "https://你的域名/livewire-xxxx/livewire.min.js?v=$RANDOM"

# 返回 200 → 源站正常，是 CDN 缓存问题
# 返回 404 → 源站还有问题，回到问题 3
```

也可以看响应头：

```bash
curl -sI 'https://你的域名/livewire-xxxx/livewire.min.js' | grep -i 'cf-cache-status'
# HIT  = 命中缓存（可能是旧内容）
# MISS = 未命中，已回源
```

### 修复

Cloudflare 后台清除缓存：

```
缓存 / Cache
  → 配置 / Configuration
    → 清除全部内容 / Purge Everything
```

中文路径：**缓存 → 配置 → 清除全部缓存**

**预防**：建议加一条缓存规则，让 Livewire 资源完全不经过 CDN 缓存：

```
缓存 → 缓存规则 → 创建规则
  当请求匹配: URI 路径 包含 /livewire-
  则: 绕过缓存 / Bypass Cache
```

## 问题 5：Cloudflare Bot Fight Mode 注入质询脚本

### 现象

页面 HTML 中多出一个 Cloudflare 质询脚本，且 Livewire 不执行。

### 根因

Cloudflare 的 **Bot Fight Mode（机器人攻击模式）** 会向页面注入 JS 质询脚本：

```html
<script>
(function(){function c(){var b=a.contentDocument||...
  d.innerHTML="window.__CF$cv$params={r:'...',t:'...'};
  a.src='/cdn-cgi/challenge-platform/scripts/jsd/main.js';
  ...}})();
</script>
```

它通过隐藏 iframe 加载验证脚本，这个过程**会阻塞页面后续 JavaScript 的执行**。Livewire 脚本恰好排在它后面，于是链式失效：

```
Cloudflare 质询脚本 → 阻塞执行
  → Livewire 没运行
    → Alpine.js 没启动
      → 登录按钮的事件处理器不存在
        → 点击无反应
```

### 诊断方法

对比源站与经 CDN 的**内联脚本数量**：

```bash
# 经 CDN
curl -s https://你的域名/admin/login | grep -c 'challenge-platform'

# 直连源站
curl -s https://127.0.0.1/admin/login -k -H 'Host: 你的域名' | grep -c 'challenge-platform'
```

若 CDN 版有、源站版没有，即为本问题。

更直观的方法：在浏览器控制台执行：

```javascript
// 正常应返回 true
typeof window.Livewire !== 'undefined'
typeof window.Alpine !== 'undefined'
// 查看内联脚本数（正常 3 个，被注入质询则为 4 个）
document.querySelectorAll('script:not([src])').length
```

### 修复

Cloudflare 后台关闭：

```
安全性 / Security
  → 机器人 / Bots
    → Bot Fight Mode → 关闭
```

中文路径：**安全性 → 机器人 → 机器人攻击模式 → 关闭**

同时检查：

```
安全性 → 设置 → 浏览器完整性检查 / Browser Integrity Check → 关闭
```

> **说明**：Bot Fight Mode 是 Cloudflare 免费版功能，它会无差别地质询所有访客
> （包括真人），对 Livewire 这类依赖 JS 的应用很不友好。
> 如果需要防机器人，建议改用 **WAF 自定义规则**（针对 `/api/*` 做限流），
> 而不是全局的 Bot Fight Mode。
>
> **注意**：该质询是**间歇性触发**的——可能只对新会话或特定浏览器指纹生效，
> 因此会出现"有时能登录、有时不能"的现象。

## 快速排查清单

按顺序执行，能定位绝大多数"点击登录无反应"问题：

```bash
# 1. 检查 session cookie 名是否正常（不应以短横线开头）
curl -sI https://你的域名/admin/login | grep -i set-cookie

# 2. 检查 Livewire JS 是否 200
U=$(curl -s https://你的域名/admin/login | grep -oE '/livewire-[a-f0-9]+/livewire\.min\.js\?id=[a-f0-9]+' | head -1)
curl -s -o /dev/null -w 'HTTP=%{http_code}\n' "https://你的域名$U"

# 3. 检查 Rocket Loader 是否在改写 script type
curl -s https://你的域名/admin/login | grep -c 'type="[a-f0-9]*-text/javascript"'

# 4. 检查是否有 Cloudflare 质询脚本
curl -s https://你的域名/admin/login | grep -c 'challenge-platform'

# 5. 对比源站直连（绕过 CDN）
curl -s -o /dev/null -w 'HTTP=%{http_code}\n' \
  'https://127.0.0.1/livewire-xxxx/livewire.min.js' -k -H 'Host: 你的域名'
```

浏览器端判断（F12 → Console）：

```javascript
typeof window.Livewire   // 应为 "object"，undefined 说明脚本未执行
typeof window.Alpine     // 应为 "object"
```

## 最终 nginx 配置参考

完整的站点配置中，与 Laravel + Livewire 相关的关键部分：

```nginx
server {
    listen 443 ssl;
    server_name 你的域名;
    root /www/wwwroot/你的项目/public;    # 必须指向 public
    index index.php;

    # ---- Livewire 动态资源（必须在静态资源规则之前）----
    location ^~ /livewire- {
        try_files $uri $uri/ /index.php?$query_string;
    }

    # ---- Laravel 伪静态 ----
    location / {
        try_files $uri $uri/ /index.php?$query_string;
    }

    # ---- PHP 处理 ----
    include enable-php-82.conf;

    # ---- 宝塔默认的静态资源规则（保持在最后）----
    location ~ .*\.(gif|jpg|jpeg|png|bmp|swf)$ { expires 30d; }
    location ~ .*\.(js|css)?$ { expires 12h; }
}
```

**顺序要点**：`location ^~` 优先级高于 `location ~`，所以 Livewire 规则写在前面就能正确拦截。

## 经验总结

这次故障的排查过程带来几点值得记录的经验：

**1. 无日志 ≠ 无问题**

Laravel 日志为空说明请求没到业务层。此时应转向检查前端 JS 与请求链路，而不是继续翻后端代码。

**2. curl 能成功不代表浏览器能成功**

`curl` 不执行 JavaScript。如果验收只测 HTTP 状态码，会漏掉所有前端 JS 相关的问题。**关键页面必须用浏览器实测**。

**3. CDN 会引入多层故障**

Cloudflare 在这次故障中贡献了 3 个问题（Rocket Loader、缓存 404、Bot 质询）。
排查时**务必对比"经 CDN"与"直连源站"的表现**，这是区分问题在哪一层的有效手段。

**4. 状态码与响应体可能不一致**

问题 3 中 curl 报 404 但内容完整，这种矛盾现象往往是多层处理（nginx 拦截 + PHP 正常输出）叠加的信号，值得深挖。

**5. 面板生成的配置需要复核**

宝塔自动生成的 `try_files ... /index.php?query_string` 缺少 `$`，是个容易忽略的坑。
引入新框架特性（如 Livewire 的动态资源路由）时，要主动检查面板默认规则是否冲突。
