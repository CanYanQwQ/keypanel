# 卡密验证模板 · Android / C++

对接本项目（卡密系统）`/api/v1/*` 接口的 **Android 原生**客户端模板。

界面为 ImGui 登录面板，协议按本项目的
**HMAC-SHA256 签名 + AES-256-GCM 传输加密** 实现，并针对 Android 上
最常见的四种破解手段做了防护：**Frida 注入 / root 改内存 / APK 二次打包 / 调试器附加**。

**零第三方依赖**：SHA-256、HMAC、HKDF、AES-256-GCM、JSON、HTTP 全部自包含，
不需要 OpenSSL / libcurl / nlohmann-json。ImGui 本身也是可选的。

## 快速接入（四步）

### 1. 复制文件

```
app/src/main/cpp/
├── 卡密/              ← 复制整个目录
├── 源码/              ← 复制（或只复制 平台剪贴板.cpp）
├── 需要的代码.cpp     ← 复制，改配置区
└── native-lib.cpp     ← 你的 JNI 入口（参考 源码/安卓接入示例.cpp）
```

### 2. 配置 CMakeLists.txt

```cmake
set(CARDKEY_DIR ${CMAKE_CURRENT_SOURCE_DIR})
include(${CARDKEY_DIR}/安卓CMake.txt)

add_library(cardkey SHARED
    ${CARDKEY_SOURCES}
    需要的代码.cpp
    native-lib.cpp
)
target_include_directories(cardkey PRIVATE ${CARDKEY_INCLUDE_DIRS})
target_link_libraries(cardkey ${CARDKEY_LIBS})
```

Release 构建会自动开启全部防护（`CARDKEY_HARDENED=1`、`-O2`、符号剥离）。

### 3. 填配置

编辑 `需要的代码.cpp` 顶部的【配置区】：

```cpp
#define 卡密_服务器地址   "https://card.example.com"    // 生产必须 HTTPS
#define 卡密_AppID        "ak_你的AppID"
#define 卡密_AppSecret    "sk_你的AppSecret"
#define 卡密_签名指纹     "你的APK签名SHA256"           // 防二次打包，务必填
```

签名指纹获取：

```bash
apksigner verify --print-certs your.apk
# 或
keytool -list -v -keystore your.keystore -alias your_alias
```

复制 `SHA256:` 后面的值（去掉冒号，大小写无所谓，模板会自动规范化）。

### 4. Java 侧注入

```java
public class MainActivity extends Activity {
    static { System.loadLibrary("cardkey"); }

    @Override
    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);

        nativeInit(this);                                    // 注入 Activity + 启动安全模块
        nativeSetDeviceId(Settings.Secure.getString(         // 设备绑定用
            getContentResolver(), Settings.Secure.ANDROID_ID));
        nativeSetSignature(getApkSignature());               // 防二次打包
    }

    /** 获取 APK 签名指纹（SHA-256 小写十六进制） */
    public static String getApkSignature() {
        try {
            PackageInfo info = Build.VERSION.SDK_INT >= 28
                ? getPackageManager().getPackageInfo(
                      getPackageName(), PackageManager.GET_SIGNING_CERTIFICATES)
                : getPackageManager().getPackageInfo(
                      getPackageName(), PackageManager.GET_SIGNATURES);

            Signature[] signs = Build.VERSION.SDK_INT >= 28
                ? info.signingInfo.getApkContentsSigners()
                : info.signatures;

            MessageDigest md = MessageDigest.getInstance("SHA-256");
            byte[] digest = md.digest(signs[0].toByteArray());

            StringBuilder sb = new StringBuilder();
            for (byte b : digest) sb.append(String.format("%02x", b));
            return sb.toString();
        } catch (Exception e) {
            return "";
        }
    }

    public native void    nativeInit(Activity activity);
    public native void    nativeSetDeviceId(String deviceId);
    public native void    nativeSetSignature(String signature);
    public native boolean nativeLogin(String cardKey);
    public native boolean nativeIsLoggedIn();
    public native String  nativeExpiresAt();
    public native String  nativeRemaining();
    public native String  nativeMessage();
    public native void    nativeHeartbeat();
    public native void    nativeLogout();
    public native void    nativeCleanup();
    public native boolean nativeUnbind(String cardKey);
}
```

### 5. 登录必须在子线程

```java
new Thread(() -> {
    final boolean ok = nativeLogin(cardKey);
    runOnUiThread(() -> updateUi(ok));
}).start();
```

主线程调用会触发 `NetworkOnMainThreadException` 并卡死界面。

## 反破解设计

### 威胁模型

Android 和桌面完全不同，**最大的威胁不是 IDA 静态分析**：

| 攻击手法 | 危害 | 本模板的防护 |
| --- | --- | --- |
| **Frida 注入 hook** | 截获卡密明文、伪造验证结果 | 四重检测（映射/线程/进程/端口） |
| **GameGuardian 改内存** | 把登录标志改成 true | 随机魔数（改 1 无效） |
| **APK 二次打包** | 改 Java 层逻辑，绕过所有 native 检测 | APK 签名校验 |
| **调试器附加** | 动态分析找关键跳转 | 双进程互检 + TracerPid |
| **inline hook** | 替换关键函数 | 函数序言校验 |
| root / 模拟器 | 批量刷卡 | 检测并上报（不直接拒绝） |

### 各项防护详解

**1. Frida 检测**（`检测Frida注入()`）

四重手段，任一命中即判定异常：

- 内存映射特征：`frida`、`frida-agent`、`frida-gadget`、`linjector`、`gum-js-loop`
- 线程名特征：`gum-js-loop`、`gmain`、`pool-frida`
- 进程扫描：遍历 `/proc/*/cmdline` 找 `frida-server`、`frida-helper`
- 端口探测：`/proc/net/tcp` 中的 27042 / 27043

**2. 双进程反附加**（`反附加守卫`）

单纯检查 `TracerPid` 有个弱点：攻击者可以在检测代码执行前就 attach，
或者 hook 掉 `fopen` 让检测永远返回"正常"。

本模板 `fork` 一个子进程，父子互检：

```
父进程（主程序）                子进程（守卫）
     |                              |
     |--- fork() ----------------->|
     |                              |
     |<-- 子进程定期检查父进程的 TracerPid 与内存映射 --|
     |                              |
  被调试时 ──> 子进程通过共享内存上报异常 ──> 父进程拒绝操作
```

用 `mmap(MAP_SHARED|MAP_ANONYMOUS)` 做跨进程通信——普通全局变量
在 fork 后各进程独立，子进程的写操作父进程看不到。

攻击者必须同时处理两个进程，成本大幅提高。

**3. Inline Hook 检测**（`检测Hook()`）

Frida / Dobby / xHook 等框架 hook 函数时，会把函数开头几个字节改成跳转指令。
本模板检查关键函数的第一条指令是否为跳转：

```
ARM64： B = 0x14000000，BL = 0x94000000，LDR literal = 0x58000000
ARM32： B = 0xEA000000，BL = 0xEB000000
```

这招对**改名版 Frida**（如 hluda，去掉了字符串特征）依然有效——
因为 hook 留下的跳转指令是无法避免的。

**4. APK 签名校验**（`签名校验.h`）

这是对抗二次打包的关键。二次打包是 Android 破解的主流：
反编译 → 改 smali → 重新签名 → 分发。**这种攻击完全绕过 native 层检测**，
因为攻击者改的是 Java 层，你的 `.so` 可能原封不动。

签名不符时，`综合校验()` 返回 false，登录被拒绝。

**5. 登录状态随机魔数**（`登录状态`）

登录标志不是 `bool`，而是每次启动随机生成的魔数。

这专门针对 GameGuardian 类工具：逆向者搜 `0/1` 定位不到登录判断；
把内存改成 `1` 也不通过——校验的是特定魔数，不是非零值。

**6. 编译期字符串加密**（`加密字符串()`）

密钥来源 `__COUNTER__ + __LINE__`，每个调用点都不同。
明文在编译期被异或加密，`.rodata` 里只有密文。

**7. 环境守卫**（`环境守卫`）

多点累计检测，而不是单点判定。各检查点按可信度加权：

| 信号 | 权重 |
| --- | --- |
| TracerPid 非 0 | 10 |
| ptrace 失败 | 10 |
| Frida 检测命中 | 10 |
| Hook 检测命中 | 10 |
| 可疑内存映射 | 5 |
| 模拟器 | 3 |
| root | 2 |

累计超过阈值才判定不可信。**攻击者必须找到并 patch 所有检查点**才能绕过，
而不是只改一个 `if`。

root 权重低是因为误报率高（很多正常用户也 root）。

**8. 完整性校验 + 内存擦除**

- 关键代码段 FNV-1a 校验和，防十六进制 patch
- AppSecret 等敏感数据 RAII 自动擦除，防内存 dump

### 检测到异常时的行为

**不直接退出**——那等于告诉破解者"这里就是检测点"。

本模板的做法是**污染签名密钥**，让服务端返回 `1004 签名验证失败`，
表现和"密钥配错了"完全一样。破解者无法定位检测点。

## 能力边界（务必阅读）

**Android 上不存在无法破解的客户端。** 上述手段能挡住绝大多数攻击，
但挡不住有经验的人用**定制版 Frida**（改名 + 去特征 + hook 掉检测函数）
持续动态调试——只能拖延，不能阻止。

真正安全的做法是**不把安全性寄托在客户端**。本项目服务端已实现：

- nonce 防重放（唯一索引，并发安全）
- 每日调用配额
- IP 白名单
- 限流（AppID + IP 滑动窗口）
- 卡密状态机（过期/用完/禁用自动生效）
- **设备绑定**
- 完整审计日志

### Android 场景的两条关键建议

**1. 务必开启设备绑定**

Android 用户 IP 会变，IP 白名单意义不大。但一张卡绑一台设备是最有效的
防共享手段——**即使客户端被完全破解，也无法在第二台设备上使用**。

**2. root 检测不要直接拒绝用户**

误报率高会流失正常用户。建议上报服务端做风控，由服务端决定策略。

如果某个场景损失足够大，正确做法是**在服务端加业务校验**
（异常行为告警、关键操作二次验证），而不是继续堆客户端防护。

## 协议要点

请求签名（与服务端 `app/Support/ApiSigner.php` 一致）：

```
canonical = METHOD \n PATH \n TIMESTAMP \n NONCE \n SHA256_HEX(raw_body)
X-Signature = HEX(HMAC-SHA256(AppSecret, canonical))
```

卡密传输加密（与服务端 `app/Support/CardTransportCrypto.php` 一致）：

```
key = HKDF-SHA256(ikm=AppSecret, salt=AppID, info="cardkey-enc-v1", L=32)
AES-256-GCM(key, IV=12字节随机, AAD=AppID)
载荷 = {"iv": base64, "data": base64, "tag": base64}
```

## 使用约束

**必须同时检查 HTTP 状态、`code`、`success`**

部分业务失败使用 HTTP 200（如 `2007` 设备不匹配）。只看 HTTP 状态会把失败
当成功。`ApiResult::success` 已封装三重判断。

**`consume` 没有幂等键**

扣次请求超时后不要自动重试，否则可能重复扣次。

**生产环境必须 HTTPS**

内置传输层只支持 `http://`，访问 `https://` 会**明确报错**而不会静默降级
（避免误以为已加密）。Android 上接入 TLS 的推荐做法是实现 `HttpTransport`
接口，用 NDK 自带的 libssl 或 BoringSSL。见 `卡密/网络请求.h` 顶部说明。

**`unbind` 的 `force=true` 不要暴露给最终用户**

服务端允许任何持有 AppSecret 的调用方强制解绑。

## 中文路径说明

NDK 的 `clang++.cmd` 包装脚本**无法处理中文路径**（实测报
`no such file or directory`）。两种解决办法：

- **方案 A（推荐）**：用 CMake + Ninja 构建。Android Studio 默认走这条路，
  不受影响。
- **方案 B**：把 `卡密/` 改名为 `cardkey/`，并批量替换
  `#include "卡密/xxx.h"` → `#include "cardkey/xxx.h"`。

## 同步规则

1. `卡密/错误码.h`
2. `docs/templates/shared/error-codes.json`
3. 其他语言客户端模板

协议变更时还需同步 `docs/API.md` 与 `docs/conformance/*.json`，
并重新运行 `协议自检`。
